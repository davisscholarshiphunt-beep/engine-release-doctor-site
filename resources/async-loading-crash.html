Cooked asset startup failures

Your package succeeded—now it crashes in AsyncLoading2

A successful package is not the same thing as a valid startup path. When a cooked build fails while creating or resolving exports, preserve the loading evidence before repeating broad cache deletions.

Published July 31, 2026 · Packaged-runtime investigation

AsyncLoading2 assertions and startup crashes can point toward an invalid cooked object relationship, class or Blueprint ancestry problem, renamed dependency, redirect, or reference chain. The final asset named in a log is not automatically the cause; it may simply be the point where a shared dependency becomes visible.

1. Preserve the exact assertion and call stack

Record the full assertion, function names, engine version, executable identity, build configuration, and complete startup log. Do not reduce the report to “the packaged build crashes.” The exact failing operation is what makes the case testable.

2. Record the final assets mentioned before failure

List the meshes, Blueprints, data assets, classes, and packages appearing near the end of the log. Mark which assets repeatedly appear across failing runs. Avoid deleting or renaming them until the reference evidence is preserved.

3. Look for a shared reference chain

Use Unreal’s Reference Viewer and dependency tools to determine whether the affected assets share:

  • a Blueprint owner or component,
  • a Data Asset or Data Table,
  • a common parent class,
  • a GameInstance, GameMode, subsystem, or startup manager,
  • a moved, renamed, or deleted dependency,
  • a stale redirector, or
  • an invalid default object or template relationship.

Epic’s Reference Viewer shows both assets that reference a selected asset and assets the selection depends on. Multiple selected assets can also reveal references they have in common.

4. Inspect Blueprint and class ancestry

Review recent changes to Blueprint parents, native base classes, class redirects, default subobjects, component templates, and startup classes. A relationship that appears repairable in the editor may still cook into an invalid export if serialized data or redirects no longer match the expected class.

5. Review moved assets and redirectors

Unreal leaves asset redirectors when assets are moved or renamed. Inspect redirectors associated with recent content changes and use the editor’s fix-up workflow deliberately. Do not assume every redirector is the cause, but do record whether the failure began after a rename, move, consolidation, plugin change, or class refactor.

6. Debug the exact packaged executable

When source and symbols are available, attach a debugger to the executable inside the packaged Binaries/Win64 directory rather than only the root bootstrap executable. Keep symbols from the exact build and inspect the package, export, template object, and expected load class at the assertion.

Shipping builds can still produce symbols when built from Visual Studio or when debug files are included through Packaging settings; the configuration affects debugging behavior but does not make all post-build inspection impossible.

7. Compare against the last working build

Record controlled differences involving:

  • asset renames or moves,
  • Blueprint reparenting,
  • native-class changes,
  • plugin updates,
  • engine upgrades,
  • redirect configuration,
  • startup classes, maps, and subsystems, and
  • cooked-content manifests.

Retest one difference at a time so that a disappearing crash produces evidence rather than another mystery.

8. Treat cache deletion as a test, not a diagnosis

Clearing Intermediate, Saved, and Derived Data Cache can test for stale generated state. When it does not change the failure, stop repeating it. Move the investigation toward references, ancestry, redirects, serialized defaults, and debugger evidence.

9. Build a compact diagnostic bundle

  • Engine version and patch
  • Development, Test, or Shipping configuration
  • Full startup log
  • Exact assertion and call stack
  • Final assets loaded before failure
  • Startup map, GameInstance, and GameMode
  • Recent asset or class changes
  • Reference Viewer findings
  • Redirector or core-redirect changes
  • Debugger findings, if available
  • Last known working build
