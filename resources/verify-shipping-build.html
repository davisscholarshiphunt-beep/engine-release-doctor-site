Pre-upload release check

Verify your Unreal Shipping build is actually Shipping

A green packaging result proves that the packaging operation completed. It does not, by itself, prove that the artifact matches the intended target, configuration, dependency set, or real distribution path.

Published July 31, 2026 · Windows, Steam, and dedicated-server readiness

Epic’s documentation distinguishes build, cook, stage, and package as separate operations. That distinction matters: the pipeline can complete while the final artifact still contains the wrong target, omits a required runtime file, or behaves differently outside the development machine.

1. Confirm the generated build command

Save the relevant AutomationTool or BuildCookRun command from the packaging output. Confirm that it names the intended:

  • project and target,
  • platform,
  • client or server role, and
  • Development, Test, or Shipping configuration.

Stop and inspect unexpected Development, DebugGame, Editor, Client, or Server targets before uploading.

2. Test for configuration-specific behavior

Epic describes Shipping as the distribution configuration that removes console commands, stats, and profiling tools that are not intended for end users. Launch the exact packaged executable and check for clues that conflict with the intended configuration:

  • Can a console be opened when it should not be available?
  • Do debug messages, stats, or profiling tools remain accessible?
  • Does the executable, receipt, window title, or log identify another target?
  • Does the artifact include unexpected symbols or development-only files?

One clue may not prove the configuration. Multiple conflicting clues justify pausing the release and tracing the pipeline.

3. Inspect the staged artifact

Compare the output against a known working release or an explicit expected manifest. Record:

  • executable and DLL names,
  • plugin binaries,
  • Pak, Utoc, and Ucas files,
  • Steam runtime files,
  • dedicated-server dependencies,
  • prerequisite installers or app-local prerequisites,
  • configuration files, maps, and chunk layout.

Packaging success does not guarantee that every file required by a target machine or storefront workflow is present.

4. Test away from the development machine

Run the artifact on a clean or representative target system when possible. Confirm that it does not silently rely on:

  • redistributables already installed on the developer PC,
  • environment variables,
  • engine or plugin files outside the package,
  • local Steam files, or
  • uncopied configuration and content.

5. Test the exact release path

Editor Play, Standalone, Development packages, local server sessions, and the final distributed Shipping artifact are different test paths. Validate the exact file set created by the method you intend to ship, including any store upload, depot, installer, launcher, or server-deployment step.

6. Compare engine versions deliberately

When the blocker begins after an engine upgrade, compare one controlled variable at a time:

  • current engine patch versus the last working patch,
  • the same project and target,
  • a clean template using the same toolchain, and
  • file manifests from both outputs.

This helps distinguish project drift from engine, plugin, toolchain, or staging regression.

7. Preserve the release evidence

  • Engine version and patch
  • Launcher or source-built engine
  • Target and configuration
  • Packaging method and generated command
  • Complete packaging log
  • Output file tree or manifest
  • Plugin list
  • Last working artifact
  • Observed configuration-specific behavior
  • Target machine or server details

Do not upload merely because packaging completed. Upload after the exact artifact has been verified for the intended configuration, expected runtime files, clean-machine behavior, and real distribution path.
