Windows release preflight

Windows long paths need more than one checkbox

A packaged build can contain a path that works on the development machine and still fail during extraction, installation, updating, or runtime access. The useful diagnosis separates three questions: is a real path exposed, is the executable long-path aware, and is the target machine configured for the same behavior?

Start with the path that will actually exist.

Do not warn merely because long paths are theoretically possible. Measure the staged path, model or observe the installed path, and preserve the exact original path before deciding whether manifest or machine capability matters.

1. Measure concrete path exposure

Microsoft defines the ordinary Win32 MAX_PATH limit as 260 characters. The total includes the drive or share prefix, directory components, filename, separators, and terminating null character. A harmless short staged path can become risky after an installer or launcher places it beneath a long customer-selected root.

Preserve these values separately:

  • the original staged relative path;
  • any staged absolute path;
  • the intended or observed installation root;
  • the resulting installed absolute path; and
  • the character length of each relevant form.

Do not silently combine malformed or relative installation-root evidence with a staged path. A modeled installed path is defensible only when the root is a valid absolute Windows drive or UNC path.

2. Keep relative and absolute paths distinct

Microsoft states that the extended-length prefix cannot be used with a relative path, so relative paths remain limited to MAX_PATH. That means a relative path that already reaches the ordinary limit is not rescued by enabling long paths on the machine.

Absolute paths are a different case. Windows can remove MAX_PATH restrictions from many common Win32 file and directory functions, but only when the application and environment meet the documented conditions. The distinction matters because the corrective action is different:

  • Overlong relative path: shorten the project, plugin, asset, staging, or filename hierarchy.
  • Overlong absolute path: prefer shortening when environments are uncertain; rely on long-path support only after verifying the executable and each target machine.

3. Verify the executable manifest

Microsoft requires an application to opt in by declaring longPathAware in its manifest. A machine policy alone does not make an arbitrary executable long-path aware.

Record the shipped executable you inspected and the explicit manifest state:

<ws2:longPathAware>true</ws2:longPathAware>

Treat an absent, false, or unverified value as different evidence states. Do not convert uncertainty into an enabled capability.

4. Verify the target-machine policy

Microsoft also requires the LongPathsEnabled registry value to exist and be set to 1. The setting can be managed by Group Policy or device-management policy. Microsoft notes that the value is cached per process and that a restart or reboot may be required for already running processes to recognize a change.

This is environment evidence, not an application guarantee. A developer machine, build agent, tester machine, customer PC, installer process, updater, extractor, antivirus component, and third-party dependency may not share the same policy or process state.

5. Do not assume every tool follows the same path rules

Microsoft documents that many, but not all, file I/O APIs support extended-length behavior. It also warns that the shell and filesystem can have different requirements. A path that one API can create may still be awkward or unusable in another tool.

For a release artifact, test the complete path through:

  • archive extraction or installer staging;
  • installation to the intended root;
  • patching or updating;
  • launcher and executable startup;
  • runtime reads and writes by plugins and dependencies; and
  • uninstall or cleanup.

6. Run a controlled retest

  1. Preserve the failing original path, full length, executable, manifest state, machine-policy state, and first observable failure.
  2. Shorten only the project, staging, install-root, or filename component that produces the exposure.
  3. Rebuild from clean staged output.
  4. Install or extract the corrected artifact on a clean target machine and repeat the same operation.
  5. If the short-path baseline passes and long-path behavior is still required, verify longPathAware=true and LongPathsEnabled=1 explicitly, restart affected processes, then repeat the same test.
  6. Stop and preserve evidence if another API, dependency, installer, updater, or shell operation still fails.

This sequence changes one variable at a time. It distinguishes a path-length blocker from a coincidental failure that happens to occur inside a deep directory.

Evidence bundle to preserve

  • Unreal Engine version and patch;
  • target platform and configuration;
  • build, staging, archive, installer, or deployment command;
  • original staged paths and their lengths;
  • validated intended or observed installation root;
  • resulting installed paths and lengths;
  • shipped executable and manifest evidence;
  • target-machine LongPathsEnabled evidence;
  • first failing process or API-visible operation; and
  • short-path and long-path controlled retest results.

What Engine Release Doctor can check

The current platform.windows diagnostic checks concrete staged or modeled installed path exposure. It keeps relative, staged-absolute, and modeled-installed paths distinct; preserves original path evidence; validates installation-root input; and reports executable and target-machine capability states separately.

It does not warn on harmless short paths. It does not edit the registry, rewrite an executable manifest, shorten project paths, change an installer, or guarantee that every Windows API or dependency supports the resulting path.
