Packaged Windows builds

Your Unreal crash may not be in the saved log

A packaged build can fail without preserving the decisive message in its ordinary Saved/Logs output. Before changing project settings at random, build a fuller evidence record.

Published July 31, 2026 · Practical diagnostic checklist

The saved Unreal log is important, but it is not the only evidence source. A process may terminate before buffered output is written, a system-level fault may occur outside the engine’s normal reporting path, or the useful message may appear only in live console output. Treat a silent or abruptly ending log as a reason to widen the evidence collection—not as proof of any one root cause.

1. Run the packaged executable with live output

Launch the actual packaged executable with:

YourGame.exe -log

Keep the console visible and capture the final messages before the process exits. Copied text is preferable, but a screenshot is better than losing transient output entirely.

2. Preserve the ordinary Unreal log

Collect the newest log from the packaged build’s Saved/Logs directory. Record whether it:

  • ends normally,
  • stops abruptly,
  • contains a fatal error or assertion, or
  • omits a message that appeared in the live console.

3. Record the exact build identity

  • Unreal Engine version and patch
  • Launcher or source-built engine
  • Development, Test, or Shipping configuration
  • Target platform and executable name
  • Packaging method used
  • Whether an earlier engine or project revision worked

Build identity matters because Development, Test, and Shipping configurations expose different debugging behavior and optimization choices.

4. Capture Windows-level crash evidence

Open Windows Event Viewer and inspect Windows Logs → Application. Preserve the event matching the failure time, including the faulting application, faulting module, exception code, and timestamp. Retain any Windows Error Reporting entry or crash dump that corresponds to the same process.

5. Record the target machine

  • CPU and GPU
  • Installed RAM
  • Windows build
  • Graphics-driver version
  • Whether the crash occurs on every tested system or only certain machines

A package that fails on one device but not another requires a different investigation than a universally broken artifact.

6. Test one controlled change at a time

Changing ten settings at once can produce a temporary workaround while destroying the evidence needed to understand the failure. Change one suspected variable, rebuild, and record the result.

Useful comparisons include:

  • current engine patch versus the last working patch,
  • Development versus Shipping,
  • a clean template versus the real project,
  • a suspected feature enabled versus disabled, and
  • an affected machine versus an unaffected machine.

7. Build a compact evidence bundle

  • Saved Unreal log
  • Captured -log console output
  • Windows crash event or dump
  • Engine and build details
  • Machine specifications
  • Plugin list
  • Last known working setup
  • Exact reproduction steps
  • Results of controlled comparison tests

The objective is not merely to collect more files. It is to determine where the failure occurs: before Unreal logging begins, during startup, during asset loading, inside a configuration-specific feature, or outside Unreal entirely.
