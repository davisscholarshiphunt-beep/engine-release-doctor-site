Release iteration performance

Why does your source-built Unreal Engine take hours to package?

If the Launcher engine packages the same project in minutes but your source engine compiles hundreds or thousands of actions on every attempt, the project may not be the real problem. The engine build may not be prepared for Launcher-like reuse.

A successful package can still be a release blocker.

During certification, launch week, or a hotfix, a two-hour package makes controlled testing dangerously slow even when the build eventually succeeds.

A documented failure pattern

In May 2026, an Unreal developer reported that the same project packaged in about two minutes with Epic's Launcher build but took up to two hours with UE 5.7 and 5.8 compiled from source. The source workflow compiled more than 1,000 actions. Other developers identified an Unreal Installed Build made through BuildGraph as the relevant comparison, and a later reply reported Launcher-like packaging behavior after using that approach.

Read the developer report on the Epic Developer Community forums.

What an Installed Build changes

Epic describes an Installed Build as a redistributable engine build containing precompiled binaries and target-platform libraries for Development and Shipping configurations. Epic provides the InstalledEngineBuild.xml BuildGraph script to create this kind of distribution from source.

Read Epic's Installed Build Reference Guide.

This does not mean every slow source package has the same cause. It means engine provenance and preparation belong in the investigation before you rewrite project code, delete content, or blame the cooker.

1. Establish a clean baseline

Package the same project, target, configuration, and platform with both environments when possible:

  • Epic Games Launcher engine
  • Your source-built engine

Record the total duration and the time spent compiling, cooking, staging, and archiving. Do not compare a clean build against an incremental build without labeling the difference.

2. Count what is being compiled

Preserve the complete packaging log and record:

  • the number of compile actions;
  • whether engine modules or only project modules are rebuilding;
  • whether ShaderCompileWorker or other engine tools rebuild;
  • whether the same actions repeat on the next unchanged package;
  • the first command that triggers the unexpected compilation.

If routine packaging resembles an engine build, that is stronger evidence than the final elapsed time alone.

3. Record engine provenance

  • Exact Unreal version, tag, or source commit
  • Launcher build, ordinary source compilation, or Installed Build
  • Compiler and Windows SDK versions
  • BuildGraph command and options, when used
  • Enabled target platforms and game configurations
  • Location and identity of the editor executable used for packaging

Two editors displaying the same Unreal version number can still represent materially different build environments.

4. Verify whether the engine is an Installed Build

Do not infer this merely because the editor launches successfully. Preserve the BuildGraph command, output location, installed-build metadata, and precompiled target binaries. Epic's current documentation shows an example using:

RunUAT.bat BuildGraph -script=Engine/Build/InstalledEngineBuild.xml -target="Make Installed Build Win64" ...

Use the options appropriate to your engine version and required platforms; do not copy a command blindly into a production pipeline.

5. Compare the second package, not only the first

After a successful package with no source changes, run the same packaging operation again and compare:

  • total duration;
  • compile-action count;
  • modules rebuilt;
  • cache reuse;
  • generated command line.

If the same large engine workload repeats, preserve that evidence before changing several build settings at once.

6. Separate diagnosis from remediation

An Installed Build may be the correct architecture for teams that rarely change engine source and need repeatable precompiled binaries. It may not fit a workflow that constantly edits the engine or requires a different deployment model. The useful diagnosis is not simply “run BuildGraph”; it is determining why routine packaging is rebuilding work you expected to reuse.

Evidence bundle for a release audit

  • Exact source commit or engine version
  • Launcher-versus-source timing comparison
  • Full packaging logs for first and repeated runs
  • Compile-action counts and representative rebuilt modules
  • BuildGraph command and output path, if applicable
  • Target platform and configuration
  • Compiler and SDK versions
  • Last known normal packaging duration
